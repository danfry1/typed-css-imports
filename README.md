# typed-css-imports

Your CSS module class names as real types, checked by plain `tsc`. A wrong class name fails in your editor and in CI, with no generated files.

![Neovim: renaming a class in a CSS module shows the type error in the component before saving, and completion offers the new name](docs/demo.gif)

```css
/* button.module.css */
.button { color: white; }
.button-primary { background: royalblue; }
```

```ts
import styles from "./button.module.css";

styles.buttonPrimary; // string
styles.buttn;
// error TS2551: Property 'buttn' does not exist on type '{ readonly button: string; ... }'. Did you mean 'button'?
```

- **Real types, not `{ [key: string]: string }`.** Every class, id, `@keyframes` and `@value` name the bundler exports, and nothing else. Typos, removed classes and `:global` names are errors.
- **Same names as your bundler.** Names come from [postcss-modules](https://github.com/madyankin/postcss-modules), the plugin Vite uses, including `localsConvention` (`camelCase`, `dashes`, …).
- **No codegen, no `.d.ts` files to commit.** Built on TypeScript 7.1 content mappers. Add a class in the CSS file and it autocompletes in your component immediately, even before you save.
- **Overrides the generic stubs.** The `declare module "*.module.css"` declarations from `vite/client` or Next.js stay in place; the mapped types take precedence.
- **Sass too.** `.module.scss` and `.module.sass` are compiled with your project's Sass first, as your bundler does, so classes generated by mixins, loops and partials are typed.
- **No runtime.** Your bundler already loads CSS modules. This package only provides types.

## Setup

Requires TypeScript 7.1 (currently in beta) and Node >= 22.12.

```sh
pnpm add -D typed-css-imports
```

`tsconfig.json`:

```jsonc
{
  "compilerOptions": {
    "allowArbitraryExtensions": true
  },
  "contentMappers": [
    {
      "package": "typed-css-imports",
      "extensions": [".module.css"], // add ".module.scss", ".module.sass" for Sass modules
      "options": { "localsConvention": "camelCase" } // optional: match your bundler's setting
    }
  ]
}
```

### Run `tsc` with `--runExternalCode`

Content mappers run package code during type-checking, so TypeScript only starts them with an explicit opt-in:

```sh
tsc --noEmit --runExternalCode
```

Editors need the same opt-in from their language-server client; see [Editor setup](#editor-setup).

### Can't use `--runExternalCode` or TypeScript 7.1? Generate files instead

`typed-css-imports generate` writes the same types to declaration files next to each module:

```sh
typed-css-imports generate [--locals-convention camelCase] src/**/*.module.css   # writes x.module.d.css.ts
typed-css-imports generate --load-path src/styles src/**/*.module.scss           # writes x.module.d.scss.ts
typed-css-imports generate --check src/**/*.module.css                           # exit 1 if any are stale
```

With `allowArbitraryExtensions`, tsc picks up `button.module.d.css.ts` for `import styles from "./button.module.css"` and no content mapper is needed.

### Check it's working

If the mapper isn't running, imports don't fail: they fall back to the `{ [key: string]: string }` stub from `vite/client` or Next.js, and typos pass silently. Add one file that turns that into an error:

```ts
// src/css-modules.check.ts
import styles from "./Button.module.css"; // any CSS module in your project

// @ts-expect-error typed-css-imports is not running if this line is not an error
styles.thisClassDoesNotExist;
```

With the mapper running, this file type-checks. If the mapper isn't running (for example an editor on a TypeScript version without content mappers, or a tsconfig.json that lost the `contentMappers` entry), it reports TS2578 "Unused '@ts-expect-error' directive", in CI and in the editor. [`examples/vite-react`](examples/vite-react/src/css-modules.check.ts) includes one.

### Sass modules

Add `.module.scss` (and `.module.sass`) to `extensions`. The modules are compiled with the `sass` or `sass-embedded` package installed in your project (the one your bundler uses), so install it if it isn't already there. If your bundler config has Sass options that affect the output, mirror them under `options.sass`:

```jsonc
"options": {
  "sass": {
    "loadPaths": ["src/styles"],                  // relative to tsconfig.json; Vite: css.preprocessorOptions.scss.loadPaths
    "additionalData": "@use \"tokens\" as *;\n"  // Vite: css.preprocessorOptions.scss.additionalData (string form)
  }
}
```

## Editor setup

The TypeScript 7.1 language server (`tsc --lsp`) starts content mappers only when the client sends `initializationOptions: { runExternalCode: true }`. Without it, CSS module imports report TS2307, or with `vite/client` types silently fall back to `{ [key: string]: string }`.

How soon types update depends on what the editor sends the server:

- **As you type:** if the editor also attaches the TypeScript server to `.module.css` (or `.module.scss`) buffers, each edit sends the unsaved CSS. The server re-runs the mapper on that text and asks the editor to refresh diagnostics, so errors in components appear before the CSS file is saved. This is what the demo above shows.
- **On save:** otherwise the server sees the CSS file when it changes on disk.

`tsc --noEmit --runExternalCode` on the command line always reads saved files.

### VS Code

Install the [TypeScript 7](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) extension (`TypeScriptTeam.native-preview`) and point `js/ts.tsdk.path` at the project's TypeScript 7.1 package, for example in your user `settings.json`:

```jsonc
{
  "js/ts.tsdk.path": "/path/to/your-project/node_modules/typescript"
}
```

The extension enables content mappers by default (`js/ts.contentMappers.enabled`), and edits to an open `.module.css` file update errors in components before you save.

Without the setting, the extension runs the TypeScript 7.0 it bundles, which has no content mappers. There are no errors: imports silently fall back to `vite/client`'s `{ [key: string]: string }`. The [check file](#check-its-working) catches this.

Tested with VS Code 1.135 and extension version 1.0.1, with the setting in user settings and `.module.css` files.

### LazyVim

In `lua/config/options.lua`:

```lua
vim.g.lazyvim_ts_lsp = "tsc"
```

In `lua/plugins/typescript.lua`:

```lua
return {
  "neovim/nvim-lspconfig",
  opts = function(_, opts)
    -- cmd and root_dir share a cache of which tsc binary to run, so take both from the same copy of lspconfig's config.
    local tsc = dofile(vim.api.nvim_get_runtime_file("lsp/tsc.lua", false)[1])
    opts.servers.tsc = vim.tbl_deep_extend("force", opts.servers.tsc or {}, {
      mason = false, -- run the project's node_modules/.bin/tsc
      init_options = { runExternalCode = true },
      -- CSS and Sass modules are attached so unsaved edits reach the server. Other stylesheets have no project and are skipped.
      filetypes = { "javascript", "javascriptreact", "typescript", "typescriptreact", "css", "scss", "sass" },
      cmd = tsc.cmd,
      root_dir = function(bufnr, on_dir)
        local ft, name = vim.bo[bufnr].filetype, vim.api.nvim_buf_get_name(bufnr)
        if not vim.list_contains({ "css", "scss", "sass" }, ft) or name:match("%.module%.s?[ac]ss$") then
          tsc.root_dir(bufnr, on_dir)
        end
      end,
    })
  end,
}
```

Tested with Neovim 0.12, LazyVim 16 and the `lang.typescript` extra. Neovim 0.11 doesn't handle `workspace/diagnostic/refresh`, so components update only when they are edited.

## Example

[`examples/vite-react`](examples/vite-react) is a Vite + React app with `vite/client` types and `localsConvention: "camelCaseOnly"` in both `vite.config.ts` and `tsconfig.json`. `pnpm --filter example-vite-react run parity` loads every CSS and Sass module (the example's and the test fixtures') through Vite and checks that the names Vite exports at runtime match the types exactly. [`examples/next-parity`](examples/next-parity) does the same with Next.js, building with webpack and with Turbopack.

## What's exported

| CSS | exported name |
|---|---|
| `.button { }`, `.a:is(.b, .c)`, `&.active` (nesting) | `button`, `a`, `b`, `c`, `active` |
| `#main { }` | `main` |
| `@keyframes spin { }` | `spin` |
| `@value brand: #0a7;` | `brand` |
| `.sm\:p-4 { }` | `sm:p-4` |
| `:global(.x)`, `:global .x` | (not exported) |
| class names in comments, strings, `url()` | (not exported) |
| `.button-primary` with `localsConvention: "camelCase"` | `button-primary` and `buttonPrimary` |
| Sass: `&-title` nesting, `@each $t in a, b { .is-#{$t} {} }`, classes from `@use`d partials and mixins | `card-title`, `is-a`, `is-b`, … |
| Sass: `%placeholder`, `$variables`, empty rules | (not exported, as in the compiled CSS) |

`composes: x from "./other.css"` is supported. Other files are never read during type-checking, because `composes` doesn't change which names a module exports.

CSS and Sass syntax errors are reported at their line and column in the module. Errors in a `@use`d file are reported at the top of the module, with the file and line in the message.

## Compared with other tools

| | [typescript-plugin-css-modules](https://github.com/mrmckeb/typescript-plugin-css-modules) | [typed-css-modules](https://github.com/Quramy/typed-css-modules), [happy-css-modules](https://github.com/mizdra/happy-css-modules) | typed-css-imports |
|---|---|---|---|
| How | tsserver plugin, editor only | Generates a `.d.ts` per module | Content mapper, inside `tsc` |
| Caught in CI | No | Yes, if generation runs first | Yes |
| Extra files | None | One per module, committed or generated in CI | None |
| Fresh clone | Works | `tsc` fails until generation runs | Works |
| Editor updates | As you type | After save, with a watcher running | As you type |
| TypeScript 7 | Not loaded (see below) | Works | Requires 7.1 |

typescript-plugin-css-modules is a tsserver plugin. The TypeScript team has said that existing tsserver plugins won't work with the TypeScript 7 codebase ([microsoft/typescript-go#2154](https://github.com/microsoft/typescript-go/issues/2154#issuecomment-3593002146)). In our test, the language server of TypeScript 7.1.0-dev.20261015.1 did not load a minimal tsserver plugin that TypeScript 5.9's tsserver loaded.

## Limits

- Next.js: with webpack, names match fully. Turbopack also omits names for empty rules (`.x { }`) and for `@value`, so those are typed but `undefined` at runtime there.
- No Less or Stylus modules.
- Editing a Sass partial doesn't update the modules that `@use` it in the editor until the module itself is edited or the language server restarts. `tsc` on the command line always compiles the current files.
- `additionalData` only in its string form; Vite's function form can't be expressed in tsconfig.json.
- Names reflect the CSS as written. PostCSS plugins your bundler runs before CSS Modules (for example ones that generate classes) are not applied.
- Default export only. Named imports (`import { button } from "./x.module.css"`) work in Vite but not in every bundler, so they aren't typed.

### Releasing

Releases are published only from CI ([`release.yml`](.github/workflows/release.yml)); `prepublishOnly` refuses a local publish.

1. Bump `version` in package.json and add a matching `## <version>` section to CHANGELOG.md. Commit to main.
2. Push a signed, annotated tag: `git tag -s v<version> -m v<version> && git push origin v<version>`.
3. The workflow checks that the tag is on main, that the commit and tag are signed, and that the version matches package.json and CHANGELOG.md, then runs the tests and the packed-package check and stages the version on npm through trusted publishing. A prerelease version (`1.2.0-beta.0`) goes to the `beta` dist-tag.
4. Approve the staged version with 2FA (`npm stage approve <id>`, or on npmjs.com). Until then it isn't installable. The GitHub release, with the CHANGELOG.md section as notes and a CycloneDX SBOM, is created after staging.
